Separare trasporto e interfaccia

Il servizio restituisce un Observable, una sorgente di notifiche: una sottoscrizione avvia la richiesta e riceve il valore oppure l’errore. Non è il risultato già disponibile. HttpClient completa normalmente dopo la risposta. Più sottoscrizioni possono inviare più richieste.

Frammento di setup e servizio: importa anche l’interfaccia Post (id, userId, title, body) nella tua applicazione.

Frammento di componente per GET. Lo stesso schema di attesa, errore e cleanup è applicato agli altri metodi della demo.

Frammenti delle chiamate per le scritture: ciascuna richiede una sottoscrizione. PUT invia la rappresentazione completa usata in questa API; PATCH sarebbe una modifica parziale e qui non viene dimostrato.

Il tipo non convalida il server

get<Post> descrive il tipo atteso per TypeScript; non controlla la struttura del JSON a runtime. In un’app reale valida i dati al confine del servizio quando il contratto lo richiede. Un errore HTTP può avere status 404 o 500; lo status 0 può indicare un problema di rete o browser.

Una richiesta alla volta

Durante l’attesa la demo disabilita le altre operazioni. L’annullamento esegue unsubscribe; takeUntilDestroyed scollega la sottoscrizione quando esci dalla pagina. finalize ripristina l’indicatore anche su errore o cancellazione. Il client interrompe l’attesa; non può garantire che una scrittura già arrivata al server venga annullata.

Risposta, anteprima e persistenza

JSONPlaceholder può restituire ID 101 a più POST. Perciò conserviamo una cronologia con ID locali univoci e manteniamo separata la lista GET. PUT e DELETE operano sui post effettivamente caricati e modificano l’anteprima dopo il successo. Una nuova GET mostra di nuovo il server: non è una prova di persistenza.

Per riprodurre un errore reale puoi provare un ID assente. I test coprono anche rete, risposte vuote, fallimenti delle scritture, recupero e uscita con richiesta pendente senza dipendere dalla disponibilità dell’API pubblica.
